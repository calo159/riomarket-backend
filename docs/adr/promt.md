# OBJETIVO (lo que exige el profesor)
El profesor entregó un diagrama base de RBAC COMPLETO y exige que el administrador gestione usuarios, ROLES y RECURSOS (no solo usuarios). El modelo es:
  usuario --(N:M)-- usuario_has_rol --(N:M)-- rol --(N:M)-- rol_has_recurso --(N:M)-- recurso
Tablas del diagrama: usuario(Usua_ID, nombre, email, telefono, direccion), usuario_has_rol(Usuario_ID, Rol_ID), rol(Rol_ID, Rol_nombre), rol_has_recurso(Rol_ID, recurso_id), recurso(idrecurso, nombre).
Lo que debe poder hacer el administrador desde la interfaz, todo con lógica y sencillez:
1. Usuarios: ver, buscar, BANEAR (suspender con motivo) y reactivar, cambiar el rol base (comprador/vendedor/administrador) y asignar o quitar roles adicionales.
2. Roles: crear, editar, desactivar y eliminar roles, y decidir qué recursos tiene cada rol.
3. Recursos: crear, editar y eliminar recursos (módulos/pantallas del sistema).
4. Menú dinámico: el menú de cada persona sale de los recursos que le dan sus roles; si se cambia un rol o un recurso, el menú cambia.
5. Panel de administración útil: moderar puestos y productos, categorías, reseñas, pedidos, pagos, cupones, verificaciones y auditoría.
6. Flujo de entrega sin conflicto de roles: el vendedor marca "ya se lo entregué al domiciliario / ya lo vinieron a buscar" (en_camino); SOLO el comprador confirma que lo recibió (entregado) o reporta "no me ha llegado"; el administrador puede resolver disputas.

# DECISIONES DE DISEÑO (ya tomadas; no las cuestiones)
1. Nueva app `apps/rbac` con 4 modelos que siguen el diagrama y usan EXACTAMENTE estos db_table: Rol -> "rol", Recurso -> "recurso", RolRecurso -> "rol_has_recurso", UsuarioRol -> "usuario_has_rol". Las dos tablas puente tienen unique (id_rol, id_recurso) y unique (id_usuario, id_rol) y FKs con CASCADE hacia las tablas puente.
   - Rol: nombre (único sin distinguir mayúsculas, 3 a 40 caracteres), descripcion, activo (default True), es_sistema (solo lectura para la API).
   - Recurso: codigo (único, regex ^[a-z][a-z0-9_.]{2,59}$), nombre, descripcion, ambito in {publico, cuenta, panel_vendedor, panel_admin}, ruta (vacía o empieza con "/"), icono (nombre de icono lucide en string), grupo (para agrupar el menú), orden (int), es_publico (visible incluso sin sesión), es_sistema (solo lectura), activo.
2. `Usuario.rol` se CONSERVA como "rol base" (comprador/vendedor/administrador): la lógica de negocio existente (crear pedidos, panel vendedor, JWT, RBAC de pedidos) depende de él. Los tres roles base existen como Rol con es_sistema=True y nombre igual al valor de Usuario.Rol. La tabla usuario_has_rol guarda TODAS las asignaciones: el rol base (sincronizado) y los roles adicionales (personalizados, aditivos). Los roles base son mutuamente excluyentes; los personalizados se suman.
3. Sincronización: señal post_save de Usuario que asegura la fila usuario_has_rol del rol base (la crea si falta; si el rol base cambió, quita la fila del rol base anterior). La señal usa get_or_create del Rol de sistema para que las fábricas de tests funcionen. Además, la migración de datos hace el backfill de usuarios existentes.
4. Permisos efectivos = unión de los recursos ACTIVOS de los roles ACTIVOS del usuario (asignados en usuario_has_rol ∪ rol base por nombre) + los recursos con es_publico=True. Usuario anónimo o suspendido: solo los públicos. NO hay atajo por rol base: si el admin le quita un recurso al rol "administrador", el acceso se pierde de verdad.
5. Módulo apps/rbac/acceso.py (sin imports pesados, para evitar ciclos): `recursos_de_usuario(usuario) -> set[str]` y `tiene_recurso(usuario, codigo) -> bool`. apps/rbac/permissions.py: fábrica `TieneRecurso(codigo)` -> clase BasePermission (uso: permission_classes = [TieneRecurso("admin.usuarios")]); cachea el set de códigos en el objeto request (no en el usuario) para no repetir consultas.

Seed idempotente `sembrar()` (en apps/rbac/defaults.py) que recibe las clases de modelo para poder usarse desde la migración de datos con modelos históricos y desde un comando `manage.py seed_rbac`. Solo AGREGA lo que falta: no sobrescribe ediciones del admin ni re-vincula recursos que el admin quitó (los vínculos por defecto solo se crean cuando el recurso se crea). Llama también a sembrar() en seed.py y seed_masivo.py.

   - catalogo | Catálogo | publico | /catalogo | es_publico=True

   - ámbito panel_admin | rol administrador: admin.resumen /admin (sin grupo); grupo "Accesos": admin.usuarios /admin/usuarios, admin.roles /admin/roles, admin.recursos /admin/recursos; grupo "Gestión": admin.verificaciones /admin/verificaciones, admin.puestos /admin/puestos, admin.productos /admin/productos, admin.categorias /admin/categorias; grupo "Operación": admin.pedidos /admin/pedidos, admin.pagos /admin/pagos, admin.cupones /admin/cupones, admin.resenas /admin/resenas; grupo "Sistema": admin.auditoria /admin/auditoria.
   Iconos lucide razonables por recurso (strings). El carrito del header queda fuera del RBAC (es estado local del cliente).
8. Candados anti-bloqueo: los roles de sistema no se eliminan, renombran ni desactivan (solo su descripción es editable). El rol "administrador" no puede perder admin.usuarios, admin.roles, admin.recursos ni admin.resumen. Los recursos de sistema no se eliminan ni desactivan, ni cambian codigo, ruta, ambito o es_publico (sí nombre, descripcion, icono, grupo, orden). Nunca puede quedar el sistema sin un administrador activo.
9. Candados anti-escalada: un admin no puede cambiar el rol ni los roles adicionales de sí mismo, ni suspenderse; solo un usuario con rol base administrador puede otorgar el rol base administrador o modificar/suspender a otro administrador; nadie que no sea administrador base puede modificar los recursos de un rol que él mismo tiene.
10. Reglas del cambio de rol BASE (POST cambiar-rol): rol destino válido y distinto; motivo obligatorio (5 a 300 caracteres); no se cambia el rol de quien tenga pedidos activos (no finales) como comprador o en alguno de sus puestos (400 indicando cuántos; las acciones de pedido dependen del rol); a vendedor: reutiliza su registro Vendedor si existe (conserva verificación) y si no lo crea en estado pendiente (no puede publicar hasta que lo aprueben); de vendedor a otro rol: sus puestos activos pasan a "inactivo" y se conserva el registro de verificación; a administrador: solo lo concede un administrador. Todo transaccional.
11. Banear = SUSPENDER (estado=suspendido, motivo obligatorio): no puede iniciar sesión, conserva rol, roles e historial; si es vendedor, sus puestos activos pasan a "suspendido"; no se tocan pedidos. Reactivar solo devuelve la cuenta a activa (los puestos los reactiva el admin desde Puestos). No se borran usuarios.
12. Tras cambiar el rol base o suspender: invalidar las sesiones del afectado (blacklist de sus OutstandingToken de rest_framework_simplejwt.token_blacklist) y notificarle (Tipo.GENERAL). Los cambios de rol↔recurso o usuario↔rol adicional no requieren cerrar sesión: los permisos efectivos se calculan en cada petición.
13. Toda acción de administración se audita (entidad "usuario" | "rol" | "recurso" | "puesto" | "producto"; acción CREAR/ACTUALIZAR/ELIMINAR; detalle con campo, de, a y motivo) y las que afectan a una persona la notifican.
14. Alcance del enforcement por recursos (sé explícito en el README): se hacen cumplir en el BACKEND con TieneRecurso los endpoints de administración nuevos (usuarios, roles, recursos, resumen, moderación de puestos y productos) y los existentes de categorías (escritura), verificaciones (listar, decidir, cédula privada), pagos (la acción solo-admin) y auditoría. Los recursos de comprador y vendedor, y admin.pedidos, admin.cupones y admin.resenas, controlan menú y rutas del frontend; las reglas de negocio de pedidos, cupones y reseñas siguen ligadas al rol base. Donde sea simple (visibilidad global de pedidos o reseñas) usa tiene_recurso en lugar de es_administrador.
